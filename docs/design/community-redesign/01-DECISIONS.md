# P1 결정 사항 (확정) — 커뮤니티 재디자인

마스터 스펙: scratchpad/design/spec/00-MASTER.md (§8 미해결 15건 중 아래 항목은 여기서 확정됨)
아래 결정은 구현자가 다시 묻지 말고 그대로 따른다. 근거가 필요하면 각 항목의 "왜".

## D1. 카테고리 택소노미 = 4종으로 교체 (데이터 마이그레이션 포함)
시안 정본(작성 시트를 8배율로 직접 판독): **질문·상담 / 식단 인증 / 식당 추천 / CKD 정보** (+ 목록 필터 칩 `전체`).
- 인기글 칩 레일에서 "식당 인증"으로 보이는 것은 저해상도 오독이며 `식단 인증`이 맞다.
- 현행 6종(식단 / 수치 변화 / 증상 고민 / 약물 / 외식 후기 / 일상 공감)은 폐기.

**매핑(결정)**
| 기존 | 신규 |
|---|---|
| 식단 | 식단 인증 |
| 외식 후기 | 식당 추천 |
| 증상 고민 | 질문·상담 |
| 약물 | 질문·상담 |
| 수치 변화 | CKD 정보 |
| 일상 공감 | **NULL(미분류)** — 새 4종 어디에도 정직하게 안 맞는다. 미분류는 `전체`에서 계속 보인다. |

**마이그레이션 규칙**
- alembic 088. `community_post.category_legacy varchar(30) NULL` 컬럼을 먼저 추가해 원본을 보존한 뒤 UPDATE. 되돌리기는 legacy 컬럼 복사 한 줄.
- **적용 전 반드시** 대상 DB에서 `select category, count(*) from community_post group by 1` 을 찍어 결과를 보고할 것. `일상 공감` 비중이 크면(예: 20% 초과) NULL 처리를 재검토하고 사람에게 물을 것.
- 서버는 create/update 에서 4종 + null 만 허용(현재는 자유 varchar). 옛 값이 들어오면 400.
- 프로덕션 트래픽은 아직 파이썬 서버(TS 전환 0%)이므로 이 마이그레이션은 지금 안전하게 준비 가능. 스토어 출시 후 전환 시점에 함께 적용.

## D2. 하단 탭 IA 는 현행 유지
시안은 하단탭을 `홈·상담·레시피·식당·전체`로 바꾸고 자유글을 레시피 하위 상단탭으로 넣지만 **P1 범위 밖**이다.
- 왜: 딥링크·routeGraph·analytics 화면명·계약 테스트가 전부 걸리고, 제품 승인이 필요한 IA 변경이다.
- P1 은 현행 커뮤니티 탭 자리에서 화면만 재디자인한다. IA 이동은 P3 후보로 남긴다.
- `tests/communityDesignContract.test.ts` 의 "상단 스토리 탭 금지" 단언은 그대로 지킨다.

## D3. 앵커드 팝오버(V2Menu)는 "선택"에만, "액션"은 시트 유지
집안 규칙(sinsin-dialog-system): 선택=V2Modal · 통보=Toast · 3지선다=시트.
시안은 6곳에서 앵커드 팝오버를 쓴다. 절충안을 확정한다:
- **팝오버(V2Menu 신설)**: 비파괴 *선택* — 피드/검색/상세의 정렬(최신순·조회순·인기순), 앨범 드롭다운(최근항목·비디오·즐겨찾기). 트리거 옆에 뜨고 바깥 탭으로 닫힌다. 밀도 최소화(사용자 취향)에 맞고, 3항목 정렬에 바텀시트는 과하다.
- **시트 유지**: 파괴적/결과가 무거운 *액션* — 게시글 더보기(수정·삭제·신고), 댓글 ⋯(수정·삭제·신고·답글), 관심없음·신고하기. 오탭 비용이 큰 항목은 손가락에서 먼 팝오버에 두지 않는다.
- V2Menu 는 `src/design-system-v2/components/V2Menu.tsx` 로 추가하고 RN Modal 안이면 ModalOverlayHost 규칙을 지킨다. 결정 근거를 docs 에 남긴다.

## D4. "오늘의 식단"은 스토리 뷰어의 두 변형이지 별도 상세가 아니다
직접 확인: 16:9 섹션 프레임도 스토리와 동일한 기하(진행 인디케이터, 하단 그라데이션 오버레이, 저염식 배지 40x21, 아바타 40, 하단 바 80)를 쓰고 댓글 입력 바가 붙어 있다.
- 한 화면 + 미디어 종횡비 변형(16:9 레터박스 / 풀블리드)으로 구현한다.
- 요구 서버 신규: **스토리 태그(저염식 등)** 와 **스토리 댓글**. 둘 다 현재 모델에 필드/표가 없다 → 서버 선행 없이는 절반만 구현된다. P1 서버 항목으로 승격.

## D5. 진입점 선(先)신설 원칙
시안이 안 그린 기존 기능 79개는 보존한다. 그중 진입점이 사라지는 3개는 **대체 진입점을 만든 뒤에만** 기존 진입점을 지운다:
- 피드 행 케밥(신고·차단) — 목록에서 신고 경로가 끊기면 스토어 심사 리스크.
- 상세 앱바의 공유·북마크.
- 헤더의 내 활동/북마크 진입.
지우기 전에 대체 경로를 눌러서 도달 가능한지 확인하는 것이 완료 조건이다.

## D6. 영상 첨부는 라벨만 정정
"사진/영상" 라벨과 달리 비디오 파이프라인이 없다. P1 은 사진 전용으로 라벨을 정직하게 고친다("사진"). 비디오는 P3.

## D7. 태그 입력 상한 5개
시안 기준 입력 상한 5개(현행 10). 서버 상한 10은 그대로 두고 **입력만** 5로 제한한다 — 기존 6~10개 태그 글은 그대로 다 보여준다.

## D8. 스토리 넘김 축 = 세로 유지, 진행 표시는 시안의 "바" 형태를 세로로 채택
사용자 지시: "알아서 유저기준 프론티어급으로". 판단 근거:
- 콘텐츠 모델이 인스타 스토리(작성자별 묶음 + 자동 넘김 타이머)가 아니라 **독립된 한 장 + 댓글**이다. 시안 뷰어에 댓글 입력 바·하트·카메라가 붙어 있다. 자동 넘김 타이머는 댓글 쓰는 사람을 방해한다 → 좌우 탭 넘김 모델은 이 콘텐츠에 안 맞는다.
- 기존 QA 근거(2026-08-06)가 구체적이고 타당하다: 인디케이터 축과 이동 축이 어긋나면 "좌우 캐러셀"로 오독된다.
**결정**: 넘김은 릴스식 **세로 유지**. 진행 표시는 현행 12개 상한의 점 스택을 버리고 **시안의 슬림한 연속 바 형태를 채택하되 좌측 가장자리에 세로로** 놓는다(길이 비례 채움).
- 얻는 것: 시안의 시각 언어(점이 아니라 얇은 바), 축 일관성(QA 결정 유지), 12개 초과 스토리에서도 정직한 진행률(현행 점은 12개에서 잘림).
- 하단 가로 바는 적용하지 않는다. 나머지 오버레이(배지·아바타·캡션·하단 바·액션)는 시안대로 픽셀 맞춘다.

## D9. 검색은 탭 안 레이어 (사용자 선택)
시안대로 커뮤니티 탭 **안에서** 검색이 열리고 상단 탭 스트립·하단 탭바가 계속 보인다.
- P0 에서 만든 `app/community/search.tsx` 푸시 라우트는 **딥링크 진입점으로 유지**하되, 그 라우트는 커뮤니티 탭으로 진입해 검색 레이어를 여는 방식으로 바꾼다(라우트가 사라지면 analytics 화면표·routeGraph 계약이 깨진다 — 표는 유지).
- 레이어 상태는 커뮤니티 탭이 소유한다. 뒤로가기는 레이어를 닫고 탭에 남는다.
- WBS 2.3 에 반영. 기존 검색 화면 본문(`CommunitySearchScreen`)은 그대로 재사용한다.

## D10. 마이크로 배지 높이는 21 — 패딩이 아니라 명시 높이로 잡는다
Phase 0-B 에서 드러난 스펙 자체의 산술 오류: §4-G2 가 제시한 방법(`V2Badge` `xs` + `paddingVertical: spacing[4]`)은 21 이 아니라 **23** 을 만든다. `caption.xSmall` 의 lineHeight 가 15 라 4+15+4 = 23. 21 을 내려면 padV 3(토큰 없음)이나 13px 라인박스(오프토큰 타이포)가 필요하다.
- **측정값이 정본이다.** §2.1 행 높이 공식이 21 을 항으로 쓰고, 그 공식이 캔버스에서 실측된 6개 높이(176/147/118/106/179/138)를 재현한다. 배지가 23 이면 행마다 최대 4px 어긋난다.
- **결정**: `V2Badge` 의 `shape="pill"` 은 스펙 문구대로 두고(23), **`MicroPill`(WBS 1.1)이 명시 높이 21 + 세로 중앙정렬로 감싼다.** 디자인이 지정한 건 패딩이 아니라 높이다.
- `communityLayout.ts` 의 `ROW.microPill = 21` 은 그대로 유지한다.

## D11. 카테고리 칩은 선택해도 굵기가 안 바뀐다
`V2Chip` 은 선택 시 폰트 굵기를 바꾸지만 §2.5(`CategoryChipRail`)는 **굵기 안 바뀜**이라고 못박는다. 굵기가 바뀌면 칩 폭이 변해 레일이 가로로 흔들리고 실측 칩 폭과도 안 맞는다.
- **결정**: `V2Chip` 에 굵기 고정 옵트인 프롭을 추가하고 `CategoryChipRail` 이 그걸 쓴다. 기존 소비자의 선택 굵기 변화는 유지(기본값 불변).
- 참고: `brandSoft` 의 1px 테두리는 이미 `paddingHorizontal` 에서 상쇄돼 바깥 박스 크기가 미선택 칩과 동일하다(Phase 0-B 가 테스트로 고정).

## D12. 새 화면들의 AnalyticsSurface 를 먼저 만든다
`V2EmptyState`/`V2ErrorState` 는 `AnalyticsSurface` 를 요구하는데, 조용한 빈 상태가 필요한 화면 대부분에 값이 없다. Phase 1 시작 전에 `src/features/analytics/events.ts` 의 유니온에 추가한다:
`community_post_detail`(S4 댓글 빈상태) · `community_reply`(S5, 새 화면) · `community_story`(S12 댓글 시트) · `community_author`(S9) · `community_connections`(S10) · `community_neighbors`(S11, 새 화면) · `community_report_other`(S6 기타사유 시트 — 지금은 `community_post_category` 를 재사용해 잘못 분류되고 있다).
화면 이름 표(`tests/analyticsScreenTable.test.ts`)의 고정 카운트도 같이 갱신해야 한다.

## D13. `V2Option` 의 55 는 실제로 57 이다
§2.17 이 같은 칸에서 "높이 55" 와 "1px 테두리"를 동시에 주장하는데 Yoga 는 테두리를 레이아웃에 포함하므로 둘 다 참일 수 없다. **DS 변경 없음** — 화면에서 55 를 기대하지 말 것.

## D14. "오프토큰 색은 back chevron 하나뿐"은 사실이 아니다
마스터 §0.1 자신이 `#07194C@5%` 를 함께 적어 두었고 §5.20 에 네 개가 더 있다(비활성 CTA 면·라벨 α, 메타 아이콘 합성 α). 방어 가능한 좁은 서술: **`#2E2F33@88%` 는 캔버스 전역에 반복되는 유일한 오프토큰 색이고 목록·상세 면에서는 유일하다.** 나머지는 단일 화면 한정이며 §5.20 이 각각의 스냅을 이미 지정했다.

## D12-정정. 분석 표면 이름은 기존 규칙을 따른다 (실측 결과)
D12 에서 제안한 이름 중 둘이 기존 규칙과 어긋나 정정됐다. 규칙은 실측된 것이다 — 기존 61개 중 **28개가 `AnalyticsScreenName` 과 문자 그대로 같고**, 나머지는 `<화면>_<판>` 이다. 화면 하나에 판 하나면 화면 토큰을 그대로 쓰고(그래야 `screen_viewed` 와 `empty_state_viewed` 를 번역표 없이 나란히 읽는다), 따로 로드·실패하는 패널·시트면 접미사를 붙인다.

확정된 9개(`src/features/analytics/events.ts` :294~320):
`community_post`(S4 본문) · `community_post_comments`(S4 댓글) · `community_reply`(S5) · `community_author`(S9, 3탭 공유 — `restaurant_reviewer` 선례) · `community_connections`(S10) · `community_neighbors`(S11) · `community_story`(S12 뷰어) · `community_story_comments`(S12 댓글 시트) · `community_report_other`(S6 기타사유)

- `community_post_detail` 은 **쓰지 않는다** — 화면 축이 이미 `community_post` 다.
- S4·S12 는 각각 **둘로 나눈다** — 본문과 댓글이 따로 로드되고 따로 실패한다. 하나로 합치면 "글이 안 열림"과 "댓글만 실패"가 구분되지 않는다.
- **라우트 등록은 파일이 생길 때 함께.** 미리 넣으면 `analyticsScreenTable.test.ts` 가 `app/` 트리와 양방향 대조해서 즉시 깨진다(83/74 고정). 표면 값만 미리 넣는 건 안전하고, 그래야 Phase 1 이 안 막힌다.

## D15. §2.18 은 낡았다 — 로컬 `QuietEmptyState` 를 만들지 말 것
마스터 §2.18 은 "`V2EmptyState` 가 20 Bold 제목 + 40 아이콘을 강제하므로 로컬 컴포넌트를 만들라"고 한다. **Phase 0-B 가 `tone="quiet"` 와 `illustration` 슬롯을 추가해 그 전제가 사라졌다.**
- 손으로 만들면 화면은 멀쩡히 나오지만 `empty_state_viewed` 가 **아무것도 안 나간다**. 댓글 빈 상태는 D12 를 만든 가장 큰 이유다.
- 같은 함정: `CommunityFeedSkeleton` 은 가시성을 `useLoadingVisible(..., { surface })` 에서 받아야만 `wait_perceived` 를 낸다.
- 계측은 컴포넌트가 자동으로 쏜다(`empty_state_viewed`·`error_state_viewed`·`sheet_opened`/`dismissed`·`wait_perceived`). 화면은 `surface` 만 넘기면 된다. 서버는 손댈 게 없다.
- **Phase 1 잔여 작업**: `CommunityReportScreen.tsx:205` 가 아직 `surface="community_post_category"` 를 넘긴다 — `community_report_other` 로 바꾸기 전까지 그 시트는 계속 잘못 분류된다.

## D16. 아바타 캐시 키는 서명을 뺀 오브젝트 경로로 (Phase 2 잔여)
`V2Avatar` 는 `expo-image` 를 쓰는데, expo-image 의 디스크 캐시는 **URL 로 키를 잡는다**. 프로필 서명 URL 은 15분마다 회전하므로 그대로 두면 **모든 아바타가 15분마다 재다운로드된다** — 아바타가 도배되는 새 디자인(피드 행·댓글·팔로워 목록·작성자 카드)에서 실사용 대역폭 문제다.
- 정본 개념은 이미 서버에 있다: `storedImageValue` 가 쿼리스트링을 떼고 오브젝트 경로만 저장한다([[image-url-single-signer]]).
- **결정**: 클라이언트도 같은 규칙으로 캐시 키를 만든다 — 쿼리스트링을 뗀 경로를 `cacheKey` 로 넘긴다. 서명이 바뀌어도 같은 이미지로 인식된다.
- 적용 범위는 아바타만이 아니다. 원격 사진을 그리는 다른 곳(레시피·식당·스토리)도 같은 함정이므로, 고칠 때 한 벌의 헬퍼로 만들 것.
- 로드 실패 상태는 불리언이 아니라 **실패한 URL** 로 들고 있어야 한다(Phase 0-D 가 그렇게 만듦) — 불리언이면 서명이 회전해도 재시도하지 않고 영원히 글리프로 남는다.

## D23. 피드의 `실시간 인기글` 레일 완성 — 순위를 되돌린다
**문제**: 시안의 피드 레일 카드는 카테고리 칩·제목·조회/좋아요/댓글만 갖고 **순위가 없다**. "실시간 인기글"인데 순위가 없으면 그냥 "글 몇 개"이고, 탭할 이유를 만드는 정보가 사라진다.
**근거**: 시안이 스스로와 모순된다 — 같은 `실시간 인기글` 이 **검색 화면(§3.2)에서는 랭킹 4행**(44h, 번호 15 Medium `primary.primary`, 번호 컬럼 25)으로 그려진다. 완성형이 같은 시안 안에 이미 있고 피드만 빠졌다.

**결정 — 가로 카드는 유지하고 순위를 넣는다.**
- 형태는 시안대로 가로 스크롤 카드(다음 카드가 살짝 보이는 peek 유지). 세로 랭킹 리스트로 바꾸면 바로 아래 `게시글` 목록과 경쟁하고 밀도가 올라간다(사용자 취향: 밀도 최소화).
- 순위 표기는 **인기글 화면과 같은 언어**를 쓴다 — 24×24 `radius.full`, bg `primary.primaryWeak`, 숫자 `label.xSmall`(13 SemiBold) `primary.primary`, `minWidth 24`(2자리 대비). §2.1 이 `PostRow` 에 정의한 랭크 원 그대로. 검색 화면의 맨 숫자 방식이 아니라 원 배지를 쓰는 이유: 카드는 독립된 면이라 자족적인 표식이 맞고, 인기글 화면과 한 언어로 묶인다.
- 헤더 행 구성도 `PostRow` 와 같다: **랭크 원 + 카테고리 칩 한 줄**(인기글 화면 실측이 그렇다).
- 개수는 5개 유지(현행 구현과 동일, peek 스크롤에 충분).

**시안에 없어서 채우는 상태들** (시안은 상태를 하나도 안 그렸다):
- **로딩**: 카드 리듬 그대로의 스켈레톤(링 스피너 금지 — 저장소 규칙).
- **오류**: 한 줄 조용한 오류 + 재시도. `StoryRail` 이 이미 이 선례를 쓴다(레일은 전면 오류 화면이 아니라 한 줄).
- **빈 상태**: **밴드 통째로 감춘다.** 인기글이 없는 피드는 그냥 `게시글` 부터 시작하면 된다 — 빈 "실시간 인기글" 밴드는 소음이다. (오류와 빈 상태는 다르다: 오류는 말하고, 빈 상태는 접는다.)
- 접근성: 카드가 순위를 읽어야 한다(`1위, {제목}`). 현행 `post.popularAccessibility` 유지.

## D24. `이런 작성자도 만나보세요` 는 시안에 **있다** — 막고 있는 건 서버뿐
**정정**: 앞서 "시안 피드에 추천 작성자 레일이 없다"고 적었는데 **틀렸다.** 못 본 프레임을 근거로 단정했다. 시안 피드는 게시글 4행 뒤에 이 섹션을 넣는다.

시안이 그리는 것(사용자 제공 프레임 기준):
- 섹션 제목 `이런 작성자도 만나보세요`, 좌 gutter 20
- 가로 스크롤 카드(다음 카드 peek), 흰 면 + 라운드
- 카드 내용: 원형 아바타 · 닉네임 · 배지 칩 1~2개(`CKD3`, `식단 인증`) · 팔로우 버튼
- 버튼 두 상태: **팔로잉 = 브랜드 솔리드**(흰 글자), **팔로우 = 브랜드 틴트**(`primaryWeak` 면 + 브랜드 글자)

**상태**: 프리미티브(`AuthorCard`/`AuthorRail`)는 WBS 1.11 로 이미 제작 중이다. 화면 삽입은 WBS 2.2.
**막는 것은 서버 하나** — `GET /community/authors/suggested`(E1)가 없다. i18n 키 `community.author.suggested` 는 원래 구현부터 고아로 남아 있었다(UI 가 없어서).

**미해결(§8-Q5)**: 피드 안 삽입 지점의 **주기**. 시안은 4행 뒤 한 번만 보여준다 — 두 번째 삽입이 있는지, 있다면 몇 행마다인지 결정 필요.

## D25. 피드 두 레일은 시안 형태를 버린다 (사용자 승인)
사용자가 "그런 레일이 있어야 한다는 게 요점이고 레이아웃·UI/UX·상호작용은 새로 해도 된다"고 승인. **마스터 §2/§3 의 해당 절과 WBS 2.1/2.2 는 이 결정으로 대체된다.**

### 지금 이야기 중 (구 `실시간 인기글` 레일)
- 시안: 가로 스크롤 카드 2개 + peek, 순위 없음, 2개 보자고 ~170pt.
- **버린 이유**: 순위는 서수라 세로로 훑는 정보다. 가로면 3위가 스와이프 뒤에 있고 서로 비교가 안 된다. 세로 피드 안 가로 스크롤은 제스처 충돌이기도 하다([[gorhom-sheet-gesture-arbitration]], [[restaurant-sheet-finger-fixes]] 선례).
- **채택**: 세로 랭킹 **3행**. 헤더에 `전체` + chevron → 인기글 화면. 각 행 = 브랜드 순위 숫자(§2.1 랭크 언어 재사용) + 제목 1줄 말줄임 + **댓글 수만**.
- **카피**: `실시간 인기글` → **`지금 이야기 중`**. "인기글"은 순위표를 약속하는데 3행만 보여준다. 목적지 화면 이름은 `인기글` 유지.
- **메타를 댓글 하나로 줄인 이유**: "실시간"이 뜻하는 건 *지금 논의 중*이고 그 신호가 댓글이다. 조회는 레일 자신이 부풀리고 좋아요는 지연 지표다. 셋을 다 주면 결정에 안 쓰이는 숫자가 시선을 나눈다.

### 비슷한 단계의 이웃 (구 `이런 작성자도 만나보세요`)
- 시안: 가로 카드(아바타·닉네임·태그칩 2개·팔로우 CTA).
- **버린 이유**: 근거 없이 팔로우를 결정하라고 한다. 정작 판단 근거인 **이 사람이 뭘 쓰는가**가 없다. 환자 커뮤니티에서 잘못된 팔로우는 의지하는 피드에 소음을 더한다.
- **채택**: 세로 **2행**. 헤더 = 제목 + **왜 이 사람이 나왔는지** 한 줄(단계 + 쓰는 주제). 각 행 = 아바타 36 · 닉네임+단계 배지 · **최근 글 제목 1줄** · 후행 팔로우 컨트롤.
- 행 누르면 프로필, 팔로우는 낙관 토글이되 **행을 그 자리에 둔다**(팔로잉으로만 바뀜). 손가락 아래에서 재배열되면 방향을 잃는다.
- **한 번만 삽입한다.** 반복 삽입은 참여 유도 패턴이고 환자들이 의지하는 피드에 소음을 더한다. (§8-Q5 "두 번째 삽입 주기"는 이 결정으로 닫힌다.)

### 두 레일 공통 상태 (시안은 하나도 안 그렸다)
로딩 = 행 리듬 스켈레톤(링 스피너 금지) · 오류 = **한 줄** + 재시도(`retryable` 게이트, `StoryRail` 선례) · 빈 상태 = **섹션 통째로 접기**. 빈 것은 접고 오류는 말한다.

## D27. `V2Chip.fixedLabelWeight` 추가됨
D11 이 요구한 프롭을 넣었다(`V2Chip.tsx`, 기본 `false` 라 기존 소비자 불변). **Medium 고정이 아니라 SemiBold 고정** — 실측상 세 섹션이 양쪽 상태 모두 13 SemiBold다. `CategoryChipRail` 의 모듈 사설 칩은 이제 이 프롭으로 은퇴시킬 수 있다.

## D28. `비슷한 단계의 이웃` 은 거짓이다 — 제목을 알고리즘이 뒷받침하는 것으로 바꾼다
D25 에서 내가 정한 제목이 **알고리즘이 하지 않는 일을 주장한다.** 서버의 추천 정렬은
`md5(seed || author_id)` 순수 회전이고 **단계도 주제도 입력에 없다**. 후보 조건은 하나뿐이다 —
**최근 90일 안에 글을 쓴 ACTIVE 사용자**.

- **결정**: 제목을 **`요즘 글 쓰는 이웃`** 으로 바꾼다. 알고리즘이 실제로 고르는 것이 그것이고,
  행에 붙는 최근 글 제목(팔로우 판단 근거)과도 결이 맞는다.
- **부제(reason)는 넣지 않는다.** `badges`(작성자의 최다 사용 태그)로 *서술적인* 줄은 만들 수 있지만
  ("~ 이야기를 나누는 이웃"), 그건 보이는 행들의 공통 태그를 말하는 것이지 **왜 당신에게 추천됐는지**가
  아니다. 인과를 주장하지 않는 이상 없는 편이 낫다.

### 단계 매칭을 하려면 — 구현 이전에 프라이버시 판단이 필요하다
데이터는 있다(`user_profile.ckd_stage`). 그러나 단계를 매칭 키로 쓰는 순간 **레일의 모든 행이
"이 사람은 당신과 같은 CKD 단계"라는 사실을 조용히 노출한다.** UI 배치로 남의 건강정보를 추론하게
만드는 것이다. 지금 커뮤니티가 노출하는 건 `author_role` 뿐이고 그마저 전원 `"CKD 환자"` 상수라
정보량이 0인데, 이건 정보량이 큰 변경이다. **제품·프라이버시 결정 사항이지 구현 사항이 아니다.**
부수적으로: 후보 풀이 줄어 얇은 단계(`STAGE_1`·`PREVENTION`)는 섹션이 더 자주 접히고,
뷰어 본인의 단계가 `UNKNOWN`/NULL 이면(벤치 분포 ~14%) 진실한 문구가 아예 없다.

**교훈**: 카피가 주장하는 것과 알고리즘이 하는 것을 같이 정할 것. 이번엔 카피를 먼저 정하고
알고리즘을 나중에 봤고, 그래서 거짓이 됐다.
